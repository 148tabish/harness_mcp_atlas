# harness-new

One task folder in, one packaged deliverable out. The harness owns everything
around harbor: it builds the task, starts the bridge the model needs, runs the
trials, grades them with harbor's Rewardkit (the pytest ledger and the judged rubric,
half each) and packages the job.

```bash
./setup.sh                                                  # once per machine
./run.sh --task input/wraysbury --model opus-5 -k 8 -n 2
```

## Prerequisites

| Requirement | Why | Check |
|---|---|---|
| Docker Engine 20.10+ (Linux) or Docker Desktop (macOS) + compose v2 | every trial is a container stack; the task containers reach the bridges as `host.docker.internal` | `docker info`, `docker compose version` |
| User in the `docker` group | the harness drives docker directly | `docker ps` without sudo |
| `uv` | builds the venvs and fetches python 3.12 | `uv --version` |
| Python 3.12 | harbor requires it; uv fetches one if the system python is older | `uv python find 3.12` |
| ~40 GB free disk | images, light servers, trial artifacts | `df -h .` |
| 8 GB+ RAM | the agent stack plus the verifier | |
| Ports 8765 and 8766 free | Claude bridge and GLM bridge, bound on every interface | `ss -ltn` (Linux) / `lsof -iTCP -sTCP:LISTEN` (macOS) |
| Outbound network | model APIs, image pulls, the rubric judge's provider | |

`./setup.sh --check` reports all of these and changes nothing.

## Credentials

**`.env` is the only file you edit.** `setup.sh` creates it from `.env.example`
on first run, reads it, and pushes what each component needs into its own config
(today that is `vendor/zbridge/.env`, which is derived and should not be edited
by hand). `run.sh` sources `.env` before every run. Re-running `setup.sh` keeps
generated secrets and only fills what is missing, so it is safe at any time.

```
.env  ──setup.sh──>  vendor/zbridge/.env   ZB_ZAI_API_KEY copied,
  │                                        ZB_BRIDGE_SECRET + ZB_THINKING_SIG_KEY
  │                                        generated once and kept
  └──run.sh──>  the run's environment      JUDGE_MODEL, JUDGE_TRANSPORT, CODEX_HOME, AWS_*
```

Each route needs its own credential. A missing one only disables that route; it
does not break the rest.

| Secret | Needed for | Where it goes |
|---|---|---|
| Codex login (`~/.codex/auth.json`) | the rubric channel (`JUDGE_TRANSPORT=codex`) | `codex login` (`codex login --device-auth` headless); the harness base64s it into the verifier as `CODEX_AUTH_B64` |
| `CLAUDE_CODE_OAUTH_TOKEN` | the rubric channel with `JUDGE_TRANSPORT=claude-code` | `claude setup-token`, then `.env` |
| Claude login | the `opus-5` route | `~/.claude/.credentials.json` or `CLAUDE_CODE_OAUTH_TOKEN` |
| z.ai API key | the GLM routes | `ZB_ZAI_API_KEY` in `.env`; `setup.sh` pushes it to the bridge |
| `ZB_BRIDGE_SECRET`, `ZB_THINKING_SIG_KEY` | GLM bridge auth | generated by `setup.sh`, never entered by hand |
| AWS credentials | only if you use the ECR image fallback | standard AWS env or `~/.aws` |

**Without a judge login the rubric channel is left out** and runs are scored on the
pytest ledger alone; every run's `verifier/judge.json` says so. `setup.sh` warns when
the login is missing and tries the configured judge model against it.

## What `setup.sh` does

1. creates `.env` from `.env.example` if it is missing, then reads it
2. checks every prerequisite above and stops on the hard ones
3. builds `.venv` and installs harbor from `vendor/harbor-0.24.0` (editable, no download);
   re-running after a vendor bump rebuilds the venv to the vendored version
4. builds the zbridge venv, pushes `ZB_ZAI_API_KEY` from `.env` into
   `vendor/zbridge/.env` and generates the two bridge secrets if absent
5. builds the Claude bridge venv
6. prints what is ready and what is missing

## The input contract

```
input/<task>/
├── instruction.md          # what the agent is told; keeps its own instruction-canary
├── task.toml               # [task] and [task.metadata] only
├── data/                   # evidence, mounted read-only at /workspace/data
├── world_data/             # overlay that seeds the Light apps
├── tests/
│   ├── test_outputs.py     # pytest channel: deterministic checks, weights 1/3/5, guards negative (charged when they fail)
│   ├── test_weights.json   # {"tests": {name: weight}, "threshold", "null_floor"}
│   ├── judge.toml          # Channel B: [[criterion]] tables for the codex judge; [judge] weight
│   └── oracle.json, old_env.json
├── solution/               # solve.py, gt_env.json, TRUTH.md - graders only
└── environment/
    ├── Dockerfile          # the agent's image
    └── light-servers/software/<App>/<file>.py   # optional server patches (see below)
```

A task may change how a Light server behaves while it is worked (answering a preview
row, re-delivering a count once the agent acts). Such a file sits under
`environment/light-servers/software/<App>/` at its vendor path and the build copies it
over the vendor copy; only `*.py` and `desc.json` travel this way, and validate refuses
anything else there. World and corpus changes belong in `world_data/`. `import_task`
carries these patches out of a built task and names any other difference it leaves behind.

`[task.metadata]` needs `apps` (the graded servers) and may add `mcp_servers`
(everything wired, graded apps plus ungraded distractors); every graded app must
also appear in `mcp_servers`, since that is the list the build wires. Ports are
read from the light servers' own `entrypoint.sh`, so they cannot drift.

`task.toml` also declares, at the top level and in `[task.metadata]`:

```toml
schema_version = "1.4"          # the contract version these blocks are written against

[task.metadata.upstream_provenance]
origin = "authored in-house from the 1883 Fishery Board report"
train_cutoff = "2026-01-31"     # the per-instance cutoff this task is safe against
license = "CC-BY-4.0"

[task.metadata.contamination_screen]
instrument = "crucible 0.4.2"
screened_on = "2026-09-22"
# each root is the file the screen read, bound to the SHA-256 of its bytes
roots = { exclusion_list = "roots/exclusions.txt@sha256:<64 hex>", freeze_table = "roots/freeze.csv@sha256:<64 hex>", near_duplicate_index = "roots/neardup.idx@sha256:<64 hex>" }
```

The harness requires these records and checks their shape. It does not verify
the provenance claims: whether a source is what the author says, and whether a
cutoff is true, are facts from outside this repository.

It does verify the screening roots. Each is `<path>@sha256:<digest>`, and the
gate re-hashes the file and compares, so the record says which bytes the screen
read and the gate confirms they are still those bytes. A bare root name is an
attestation and fails; so does a root the gate cannot read, a digest that no
longer matches, or `unresolved` - a screen that could not run is not a screen
that found nothing.

`tests/test_weights.json` also declares `null_floor`: the reward an empty
submission earns, which a real run has to beat. Measure it with a nop run; do
not assert it.

The harness rejects an input folder that carries `[agent]`, `[verifier]` or
`[environment]` blocks: it owns those.

It also enforces the private boundary between what the grader knows and what the
agent can read:

- no `gt_env.json`, `oracle.json`, `TRUTH.md`, `solve.py` or `solve.sh` under
  `data/` or `world_data/`, and no mention of them in `instruction.md`
- the canary in `instruction.md` must be the one this task recorded in
  `.identity.json`, so a copied instruction cannot trace a leak to the wrong task
- at most 2% of the wording in `TRUTH.md` and `solve.py` may reappear in what the
  agent can read (8-word shingles). `gt_env.json` is excluded from that scan: it
  is the world the oracle leaves behind, so it restates the seed world by
  construction, and scanning it would measure that construction rather than a leak
- `environment/Dockerfile` must pin every `FROM` to a `@sha256:` digest
- two tasks whose `instruction.md` states the same problem are flagged as a
  collision, tracked in `out/task_registry.json`

None of this establishes that a task is uncontaminated. It establishes that named
checks ran. Overlap below the threshold is exactly what a deterministic check
cannot see.

To turn an existing built task into an input folder:

```bash
.venv/bin/python -m harness.import_task --from ../fixed-tasks/<uuid> --name <name>
```

## Running

```bash
./run.sh --task input/wraysbury --model opus-5 -k 8 -n 2
./run.sh --task input/wraysbury --model opus-5 --effort low -k 8 -n 2
./run.sh --task input/wraysbury --only build            # materialise only
./run.sh --task input/wraysbury --only package --job out/jobs/<name>
./run.sh --task input/wraysbury --model opus-5 --no-package
```

| Flag | Meaning | Default |
|---|---|---|
| `--model` | `opus-5`, `glm-5.3-flash`, `glm-5.3`, `glm-4.6v` | `opus-5` (`defaults.model` in `config/models.yaml`) |
| `--effort` | reasoning effort, Claude only | unset |
| `-k` / `-n` / `-r` | attempts / concurrent / retries | 8 / 2 / 2 |
| `--threshold` | pass@k threshold, 0-1 | the task's `tests/test_weights.json`, else 0.7 |
| `--judge-model` | the model the rubric judge runs as | `JUDGE_MODEL` in `.env`, else `config/models.yaml` (`gpt-5.6-sol`) |
| `--judge-transport` | `codex` (ChatGPT login) or `claude-code` | `JUDGE_TRANSPORT`, else `codex` |
| `--only` | `validate`, `build`, `run`, `regrade`, `report`, `package` | all but regrade |

Output: `out/build/<uuid>/` (the task), `out/jobs/<job>/` (trials plus
`harness_summary.json`), `out/packaged/<uuid>/` (the deliverable).

Running the same task again adds runs rather than replacing them: the packager takes
every job under `out/jobs/` that ran the task as it is built now (same
`task_checksum`), numbers the trials `run_1..run_N` by start time across those jobs,
and recomputes `pass@N.json` and `pass_summary.json` over all of them. Trials of an
older build are left out and named (`--any-checksum` in `harness.package_task` takes
them anyway). `--only regrade --job <job>` re-runs the verifier over a finished job's
recorded artifacts into `<job>-regraded`; a regraded trial replaces its original when
packaged.

## Scoring

Grading runs in the separate verifier container (`tests/Dockerfile`, built from the
harness template) with harbor's **Rewardkit**, pinned at `harbor-rewardkit==0.2.3`.
`tests/test.sh` rebuilds the trajectory, restores the collect hook's snapshot and
server log, runs pytest for the reports, then `rewardkit /tests/reward`:

- **pytest channel** — `reward/pytest/ledger.py`, one criterion that calls every test
  in the author's `tests/test_outputs.py` with the weights in `test_weights.json`:
  `pytest = max(0, (earned − charged guards) / total positive weight)`. A guard
  (negative weight) is charged when it fails; a task written to the older template
  polarity says `"guard_polarity": "pass_charges"`. A test that returns nothing or
  raises counts as failed, with the reason in `grade_report.json`.
- **rubric channel** — `reward/rubric/judge.toml`, compiled at build from the author's
  `tests/judge.toml` (the built task carries only the compiled copy; `harness.import_task`
  reconstructs the source from it) (one `[[criterion]]` per item: `id`, `description`, `weight`,
  `is_positive`, `evaluation_target`; the older `tests/rubric.json` is accepted too).
  Rewardkit's agent judge (`codex` or `claude-code`, model `JUDGE_MODEL`) answers each
  criterion yes/no from its own working directory, which holds the task instruction,
  the agent's final message, a copy of the delivered files and the trajectory (harbor's
  ATIF, or the one `test.sh` rebuilt from the agent log). Two judgings of the same
  trajectory differ within the judge's own variance (a few points of 78 on coldchain). The arithmetic is the authors' own:
  `rubric = max(0, (earned − penalised) / total positive weight)`, a "yes" on a reward
  criterion earns its weight, a "yes" on a penalty criterion charges it.
- **Combined** — `reward/reward.toml`, harness policy, the same for every task:
  `reward = 0.5 · pytest + 0.5 · rubric`. `reward.json` carries all three keys. Without
  a judge (no login, no model, `JUDGE_SKIP=1`, a judge that timed out) the rubric
  channel is left out, `reward = pytest`, and `judge.json` records why. A judge that
  cannot run is never scored as zero.
- **What each run records** — `verifier/reward.json`, `reward-details.json` (every
  test and every criterion with the judge's reasoning), `grade_report.json`,
  `judge.json` (`ran`, `transport`, `model`, the Rewardkit and codex versions), plus
  `test-stdout.txt`, `junit.xml`, `ctrf.json`, and `state_capture_failed.txt` when the
  collect hook shipped no snapshot or server log. Every score in the bundle is on the
  0-1 scale (Rewardkit writes reward.json to 4 decimals; grade_report.json keeps 6).
- A task that ships its own `tests/test.sh`, `Dockerfile` or `grade.py` does not
  replace this: `validate` and `build` say so and the harness verifier runs anyway, so
  every task is graded the same way.

## Models

`config/models.yaml` maps each model to a bridge. GLM-5.3 is text-only: images
reach it as `[image omitted: this model cannot view images]`. GLM-5.3-flash and
the `v` models read images. The runner patch in
`vendor/harness-levi-bridge/harbor_agent/openhands_bridge_agent.py` applies three
GLM-only settings that are needed for vision to work at all: `supports_vision`,
`force_string_serializer=False` and `max_output_tokens=16384`.

## Handing this to someone else

Copy the `harness-new/` folder, then on the new machine:

1. `./setup.sh --check` and fix whatever it reports
2. `./setup.sh` once, which writes `.env`
3. put the z.ai key in `.env`, run `codex login`, then `./setup.sh` again to push it through
4. `./run.sh --task input/<task> --model <model> -k 1 -n 1` as a smoke test

Two caveats worth stating plainly: the codex login is personal, so each operator
needs their own or the rubric goes unscored; and only one bridge can hold each
port, and the harness refuses to use one it did not start (there is no
override), so stop any other copy's bridge before running.

## Running on macOS and Linux

The same checkout runs on a Mac (Docker Desktop, arm64) and on a Linux box (Docker
Engine, usually amd64) with no per-machine configuration:

- **Addresses.** The bridges bind `0.0.0.0`. Task containers reach them as
  `host.docker.internal`: Docker Desktop resolves that name itself, and on a Linux
  engine the compose template aliases it to the docker0 gateway (`extra_hosts:
  host.docker.internal:host-gateway`, engine 20.10+). The harness probes the bridges on
  loopback. `AURORA_CC_BRIDGE_HOST=127.0.0.1` / `ZB_HOST=127.0.0.1` in `.env` keep a
  bridge off the LAN on a Mac; on Linux that would hide it from the containers.
- **Images.** Every base image the harness builds from is pinned to a multi-arch digest,
  so the same Dockerfiles build on arm64 and amd64. `./setup.sh --check` inspects each
  pinned `FROM` for the host's platform. The `Dockerfile.ecr` variants are the ECR eval
  images, linux/amd64 only; they are not used unless `JUDGE_DOCKERFILE=Dockerfile.ecr`.
- **Resources.** `setup.sh` reads the CPUs and memory the docker engine actually has
  (the Docker Desktop VM on a Mac, the machine on Linux) and compares them with
  `defaults.concurrent` in `config/models.yaml`: about 3 GB and 2 CPUs per concurrent
  trial, plus 4 GB for the verifier, the bridges and the OS.
- **The Claude login** is read from `CLAUDE_CODE_OAUTH_TOKEN` (headless, both OSes),
  `~/.claude/.credentials.json` (Linux) or the Keychain (macOS, with
  `AURORA_CC_WRITE_BACK_KEYCHAIN=1` so a refresh is written back).
- **Shell tools.** The scripts use only what GNU and BSD share; where they differ
  (`df`, `ss`/`lsof`, `base64`) both forms are tried.
- **Case.** A Mac's filesystem ignores letter case and a Linux one does not, so
  `validate` refuses a `COPY` in the agent Dockerfile whose source exists only in a
  different case.

## Provenance and contamination records

`validate` reports a missing `upstream_provenance` or `contamination_screen`
record in `task.toml [task.metadata]` as a warning and builds the task anyway.
Set `ATLAS_STRICT_PROVENANCE=1` to refuse such a task instead.

## Judge models

The rubric judge is whatever `--judge-model` / `JUDGE_MODEL` / `config/models.yaml`
names (default `gpt-5.6-sol`), reached through the transport in `JUDGE_TRANSPORT`
(default `codex`, the Codex CLI with the operator's ChatGPT login). The value used is
written into every run's `verifier/judge.json` and into `report.json`,
`pass_summary.json` (`judge_models`) of the bundle, so a job always says what judged
it. Which models a ChatGPT login may run depends on its plan: a Pro login (plan
`promax` in `~/.codex/auth.json`) accepts `gpt-5.6-sol`, `gpt-5.6-terra` and
`gpt-5.6-luna`; a Plus login accepts terra and luna only, and `gpt-5.5`, `gpt-5.6` and
`gpt-5.6-sol` fail with "model is not supported when using Codex with a ChatGPT
account" (both probed 2026-10-22, codex 0.162). `setup.sh` tries the chosen model
against the current login and warns. A different judge is a different benchmark, so keep it fixed across
the runs you compare.

## Running a task that is already built

A folder that is already a harbor task (it carries `[agent]`, `[verifier]`,
`[environment]` and its own `tests/Dockerfile`, `test.sh`, `grade.py`) is not an
input folder. `harness.import_task` turns it into one, but the result still has
to meet the contract above (`judge.toml`, `tests` in `test_weights.json`), and
the harness build replaces its compose file and verifier with the templates (the
author's verifier files are reported and not used). To run such a task
exactly as built, stage it under `out/build/<uuid>/`, make sure its `[agent]`
block is `network_mode = "public"` (an allowlist of the model APIs blocks the
bridge on the docker host), keep a `.identity.json` with that uuid in an input
folder of the same task, and run only the steps after build:

```bash
./run.sh --task input/<task> --model opus-5 --effort high -k 1 -n 1 --only run --only report
```

## Security boundaries

- **Bridge upstream.** The Claude bridge forwards only to `https://api.anthropic.com`.
  Every forwarded request carries the live OAuth token, so `AURORA_CC_UPSTREAM`
  pointing anywhere else refuses to start. A genuine proxy is added by host in
  `AURORA_CC_UPSTREAM_ALLOW`; the comparison is on the parsed host, never a
  substring, and credentials, paths or queries in the URL are refused.
- **Workspace containment.** The filesystem MCP tools resolve every path and
  refuse anything outside `/workspace`, `..` and symlinks included.
- **Server loading.** The light servers import only the servers `entrypoint.sh`
  declares; an `app.py` anywhere else in the tree is reported and not run.
- **No shell.** The harness passes arguments as lists; nothing from config or a
  URL is interpolated into a shell command.
